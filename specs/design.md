## 1. Архитектура и основной процесс

Приложение реализуется как REST-сервис с разделением ответственности между слоями. Бизнес-логика проверки правил ККД, расчёта метрик и сравнения прогонов отделена от REST API и слоя доступа к данным.

### Основные компоненты приложения

- `controller` реализует сгенерированные интерфейсы `openapi.api`, проверяет параметры и преобразует результаты сервисов в модели ответов из `openapi.model`.
- `service` координирует выполнение прогонов и чтение результатов. Для расчётов вызывает доменную логику, для доступа к данным использует репозитории.
- `domain.rule`, `domain.metric` и `domain.comparison` содержат правила проверки, расчёт метрик и сравнение прогонов. Они работают с типами из `domain.model` и не зависят от Spring, JPA или PostgreSQL.
- `repository` выполняет запросы к PostgreSQL. `entity` содержит JPA-сущности, а `repository.projection` описывает строки, возвращаемые запросами.
- `readmodel` содержит модели чтения результатов ККД: список прогонов, сводку и страницу проблем. Страницу проблем используют репозиторий, сервис и контроллер.
- `exception` содержит общие исключения приложения. HTTP-коды и формат ошибки определяет обработчик в `controller`.

Контракт HTTP API хранится в [`kkd.yaml`](../src/main/openapi/kkd.yaml). На фазе Maven `generate-sources` OpenAPI Generator создаёт интерфейсы Spring MVC с маршрутами и параметрами запросов, модели ответов в виде Java `record` и перечисления. Сборка записывает их в `target/generated-sources/openapi`. Сгенерированные типы используются на границе HTTP API. Сервисы возвращают собственные модели из `readmodel`.

### Основной процесс выполнения прогона

1. Получение активных целей и связанных с ними ключевых результатов.
2. Проверка данных по выбранным правилам ККД.
3. Формирование списка найденных проблем.
4. Создание прогона ККД со ссылкой на прогон для сравнения, если он указан.
5. Сохранение найденных проблем, связанных с прогоном.
6. Сохранение метрик прогона по каждому подразделению с учётом его поддерева и перевод прогона в `COMPLETED`.
7. При запросе статистики — чтение сохранённых метрик и сравнение результатов текущего и предыдущего прогонов.

## 2. Проверка правил ККД

Логика каждого правила реализуется отдельным компонентом проверки.

Rule Checker получает данные цели и связанных с ней ключевых результатов и возвращает список обнаруженных проблем. Компоненты проверки не зависят от REST API и слоя доступа к данным.

Реализуются следующие правила:

### 2.1. GOAL_NO_OWNER

Проверяются только активные цели.

Если у активной цели отсутствует ответственный, создаётся проблема:

- код правила: `GOAL_NO_OWNER`;
- объект: цель;
- важность: `critical`.

Ответственный считается отсутствующим, если `owner_id` равен `null`, является пустой строкой или состоит только из пробельных символов.

### 2.2. GOAL_NO_KR

Проверяются только активные цели.

Если у активной цели отсутствуют ключевые результаты, создаётся проблема:

- код правила: `GOAL_NO_KR`;
- объект: цель;
- важность: `critical`.

### 2.3. KR_WEIGHTS_SUM

Проверяются ключевые результаты активной цели.

Вес ключевого результата хранится как целое число. Дробные значения веса не используются.

Сумма весов проверяется, только если у активной цели есть хотя бы один ключевой результат. Для цели без КР срабатывает `GOAL_NO_KR`, а `KR_WEIGHTS_SUM` не применяется.

Если хотя бы у одного КР вес не указан (`null`) или сумма всех весов отличается от `100`, создаётся проблема:

- код правила: `KR_WEIGHTS_SUM`;
- объект: цель;
- важность: `major`.

### 2.4. KR_STALE_PROGRESS

Проверяются ключевые результаты активных целей.

Давность обновления считается в календарных днях от даты снимка прогона. При чтении из БД `snapshot_date` и `last_fact_update` преобразуются из `Instant` в `LocalDate` в UTC, чтобы результат не зависел от часового пояса машины.

Если дата последнего обновления фактического значения более чем на 45 календарных дней раньше даты снимка, создаётся проблема. Ровно 45 дней не считается нарушением.

Если `last_fact_update` отсутствует (`null`), ключевой результат также считается нарушающим правило.

Параметры проблемы:

- код правила: `KR_STALE_PROGRESS`;
- объект: ключевой результат;
- важность: `minor`.

## 3. Модель данных

### Основные сущности

| Сущность | Назначение |
| :--- | :--- |
| **unit** | Подразделение. Поддерживает иерархическую структуру. |
| **goal** | Цель сотрудника, относящаяся к подразделению и при необходимости связанная с родительской целью. |
| **key_result** | Ключевой результат, связанный с целью. |
| **kkd_rule** | Справочник правил контроля качества данных. |
| **kkd_run** | Прогон ККД для определённой даты снимка. |
| **kkd_issue** | Проблема, обнаруженная в рамках конкретного прогона. |
| **kkd_run_metric** | Значение метрики для пары «прогон — подразделение». |

### Связи между сущностями

- Одно подразделение может содержать несколько дочерних подразделений.
- Иерархия подразделений реализуется через `unit.parent_id`.
- Одно подразделение может содержать несколько целей.
- Одна цель может быть связана с родительской целью через `goal.parent_goal_id`.
- Одна цель может содержать несколько ключевых результатов.
- Один прогон может содержать несколько найденных проблем.
- Каждая проблема связана с одним прогоном и одним правилом.
- Один прогон может ссылаться на предыдущий прогон через `kkd_run.compared_to_run_id`.

### Структура таблиц

#### unit

- `id`
- `name`
- `parent_id`

Связи:

```text
unit.parent_id -> unit.id
```

`parent_id = null` означает подразделение верхнего уровня.

#### goal

- `id`
- `unit_id`
- `parent_goal_id`
- `title`
- `owner_id`
- `status`
- `deadline`
- `created_at`
- `updated_at`

Связи:

```text
goal.unit_id -> unit.id
goal.parent_goal_id -> goal.id
```

`parent_goal_id` используется для поддержки каскадирования целей.

`owner_id = null` допускается на уровне БД, поскольку отсутствие ответственного является одним из проверяемых нарушений ККД.

#### key_result

- `id`
- `goal_id`
- `title`
- `weight`
- `target_value`
- `fact_value`
- `last_fact_update`
- `created_at`
- `updated_at`

Связь:

```text
key_result.goal_id -> goal.id
```

`weight` хранится как целое число.

Ограничение:

```text
0 <= weight <= 100
```

`weight` и `last_fact_update` допускают `null`. Отсутствующие значения выявляют правила `KR_WEIGHTS_SUM` и `KR_STALE_PROGRESS` соответственно.

#### kkd_rule

- `id`
- `code`
- `name`
- `description`
- `severity`
- `is_active`

Уровни важности хранятся как `CRITICAL`, `MAJOR`, `MINOR`. В API они передаются в нижнем регистре.

#### kkd_run

- `id`
- `status`
- `snapshot_date`
- `compared_to_run_id`
- `started_at`
- `completed_at`

Связь:

```text
kkd_run.compared_to_run_id -> kkd_run.id
```

Для первого прогона:

```text
compared_to_run_id = null
```

#### kkd_issue

- `id`
- `run_id`
- `rule_id`
- `unit_id`
- `object_type`
- `object_id`
- `severity`
- `description`
- `detected_at`

Связи:

```text
kkd_issue.run_id -> kkd_run.id
kkd_issue.rule_id -> kkd_rule.id
kkd_issue.unit_id -> unit.id
```

`unit_id` хранит подразделение цели на момент прогона. Для проблемы ключевого результата сохраняется подразделение его цели.

Поддерживаемые типы объектов:

```text
GOAL
KEY_RESULT
```

При сравнении прогонов идентичность проблемы определяется комбинацией:

```text
rule_id + object_type + object_id
```

Использование `object_type` исключает неоднозначность, если идентификаторы целей и ключевых результатов могут совпадать.

#### kkd_run_metric

- `id`
- `run_id` — ссылка на `kkd_run.id`.
- `unit_id` — ссылка на `unit.id`.
- `metric_code`
- `value`
- `calculated_at`

Комбинация `run_id, unit_id, metric_code` уникальна. Значение метрики допускает `null`.

## 4. Работа с иерархией подразделений

Метрики и проблемы для подразделения рассчитываются с учётом:

- самого запрошенного подразделения;
- всех непосредственных дочерних подразделений;
- всех дочерних подразделений на последующих уровнях вложенности.

Таким образом, выборка данных для `unit_id` должна рекурсивно учитывать всё поддерево подразделения.

Сводка читает метрики поддерева, сохранённые для запрошенного подразделения и прогона. При фильтрации проблем текущая иерархия определяет набор подразделений, а принадлежность каждой проблемы берётся из сохранённого `kkd_issue.unit_id`.

Эта модель предполагает неизменность оргструктуры для согласованного чтения исторических результатов. После переноса ветви метрики и проблемы могут относиться к разному составу подразделений. Версионирование иерархии не реализовано; варианты устранения ограничения описаны в acceptance.md.

## 5. Расчёт метрик

Метрики рассчитываются для выбранного прогона и подразделения с учётом всех его дочерних подразделений.

В расчётах используются только активные цели и связанные с ними ключевые результаты.

### 5.1. Доля корректных целей — `clean_goals_share`

Показывает долю активных целей, для которых в текущем прогоне не найдено ни одной проблемы ККД.

```text
clean_goals_share =
    количество активных целей без проблем
    /
    количество всех активных целей
    * 100
```

Единица измерения:

```text
%
```

Рост значения означает улучшение качества данных.

### 5.2. Среднее количество проблем на цель — `issues_per_goal`

Показывает среднее количество найденных проблем на одну активную цель.

```text
issues_per_goal =
    количество найденных проблем
    /
    количество активных целей
```

Рост значения означает ухудшение качества данных.

### 5.3. Доля целей с ответственным — `goals_with_owner_share`

Показывает долю активных целей, у которых заполнен ответственный.

Заполненность `owner_id` определяется так же, как в правиле `GOAL_NO_OWNER`.

Общий предикат `GoalQuality.hasOwner` используется и правилом, и калькулятором метрик. Отсутствие finding не подменяет проверку owner_id.

```text
goals_with_owner_share =
    количество активных целей с ответственным
    /
    количество всех активных целей
    * 100
```

Единица измерения:

```text
%
```

Рост значения означает улучшение качества данных.

### 5.4. Доля целей с корректной суммой весов КР — `goals_with_valid_kr_weights_share`

Показывает, какая доля активных целей с ключевыми результатами проходит проверку `KR_WEIGHTS_SUM`: все веса заполнены, их сумма равна `100`.

Правило и метрика используют общий предикат `GoalQuality.hasValidWeights`; расчёт доли не зависит от наличия finding с определённым строковым кодом.

```text
goals_with_valid_kr_weights_share =
    количество активных целей со всеми заполненными весами КР и суммой весов = 100
    /
    количество активных целей, имеющих хотя бы один КР
    * 100
```

Единица измерения:

```text
%
```

Рост значения означает улучшение качества данных.

### Значения метрик при отсутствии данных

Если знаменатель метрики равен `0`, её значение сохраняется в `kkd_run_metric.value` как `NULL` и возвращается в API как `null`.

Например, если в выбранном подразделении отсутствуют активные цели:

```json
{
  "key": "clean_goals_share",
  "value": null
}
```

## 6. Расчёт дельты метрик

Для каждой метрики возвращаются:

- `value` — значение текущего прогона;
- `previous` — значение сравниваемого прогона;
- `delta` — разница между текущим и предыдущим значениями;
- `trend` — направление изменения.

Дельта рассчитывается по формуле:

```text
delta = value - previous
```

### Определение trend

Для метрик, рост которых означает улучшение:

```text
delta > 0 -> better
delta < 0 -> worse
delta = 0 -> same
```

К ним относятся:

- `clean_goals_share`;
- `goals_with_owner_share`;
- `goals_with_valid_kr_weights_share`.

Для метрик, рост которых означает ухудшение:

```text
delta > 0 -> worse
delta < 0 -> better
delta = 0 -> same
```

К ним относится:

- `issues_per_goal`.

Поддерживаемые значения:

```text
better
worse
same
```

### Первый прогон

Если у прогона отсутствует `compared_to_run_id`, сравнение не выполняется.

В этом случае:

```json
{
  "previous": null,
  "delta": null,
  "trend": null
}
```

Поля `compared_to` и `delta` верхнего уровня в ответе `/api/kkd/summary` также возвращаются как `null`. Если сравниваемый прогон есть, но одно из значений метрики отсутствует, у этой метрики `delta` и `trend` равны `null`.

## 7. Сравнение проблем между прогонами

Для сравнения используется текущий прогон и прогон, указанный в `compared_to_run_id`.

Сервис не определяет предыдущий прогон самостоятельно по дате: связь между сравниваемыми прогонами задаётся явно.

### 7.1. Идентичность проблемы

Проблемы считаются одинаковыми, если совпадают:

```text
rule_id
object_type
object_id
```

Описание проблемы и уровень важности не участвуют в определении идентичности.

### 7.2. Классификация проблем

Пусть:

```text
currentIssues  — множество проблем текущего прогона
previousIssues — множество проблем предыдущего прогона
```

Тогда:

| Категория | Условие |
| :--- | :--- |
| **new** | Проблема есть в текущем прогоне, но отсутствует в предыдущем. |
| **persisting** | Проблема присутствует в обоих прогонах. |
| **resolved** | Проблема присутствовала в предыдущем прогоне, но отсутствует в текущем. |

Формально:

```text
new = currentIssues - previousIssues

persisting = currentIssues ∩ previousIssues

resolved = previousIssues - currentIssues
```

Для первого прогона сравнение проблем отсутствует.

---

## 8. Разбивка проблем по важности

Для каждой категории важности возвращается количество проблем текущего и предыдущего прогонов.

Поддерживаются:

```text
critical
major
minor
```

Для каждой категории рассчитываются:

```text
current
previous
delta
```

Дельта:

```text
delta = current - previous
```

Для первого прогона:

```text
previous = null
delta = null
```

## 9. REST API

### 9.1. Получение списка прогонов

```http
GET /api/runs
```

Возвращает список прогонов ККД.

Для каждого прогона возвращаются:

- идентификатор;
- статус;
- дата снимка;
- идентификатор сравниваемого прогона;
- количество найденных проблем.

Пример ответа:

```json
{
  "content": [
    {
      "id": 2,
      "status": "COMPLETED",
      "snapshot_date": "2026-10-26",
      "compared_to_run_id": 1,
      "issues_count": 10
    },
    {
      "id": 1,
      "status": "COMPLETED",
      "snapshot_date": "2026-10-19",
      "compared_to_run_id": null,
      "issues_count": 7
    }
  ]
}
```

| Параметр | Тип | Обязательный | Описание |
| :--- | :--- | :--- | :--- |
| `run_id` | Long | Да | Положительный числовой идентификатор прогона ККД. |
| `unit_id` | Long | Нет | Положительный числовой идентификатор подразделения. Фильтр учитывает дочерние подразделения. |
| `rule_code` | String | Нет | Фильтр по коду правила ККД. |
| `severity` | String | Нет | Фильтр по важности: `critical`, `major`, `minor`. |
| `limit` | Integer | Нет | Число проблем в ответе: от `1` до `500`. По умолчанию `5`. |
| `offset` | Integer | Нет | Число подходящих проблем, которые нужно пропустить. По умолчанию `0`. |

Проблемы сортируются по возрастанию ID. Поле `total` содержит число проблем, прошедших фильтры, до применения `limit` и `offset`.

Размер страницы по умолчанию выбран для демонстрации. Во втором демопрогоне 10 проблем, поэтому два запроса возвращают по пять записей, а `total` в обоих ответах равен `10`.

```http
GET /api/kkd/issues?run_id=2
GET /api/kkd/issues?run_id=2&offset=5
```

Пример запроса:

```http
GET /api/kkd/issues?run_id=2&unit_id=2&rule_code=GOAL_NO_KR&severity=critical
```

Пример ответа:

```json
{
  "content": [
    {
      "id": 13,
      "rule_code": "GOAL_NO_KR",
      "object_type": "GOAL",
      "object_id": 14,
      "severity": "critical",
      "description": "У активной цели отсутствуют ключевые результаты."
    }
  ],
  "limit": 5,
  "offset": 0,
  "total": 1
}
```

## 10. Валидация и обработка ошибок

Spring MVC проверяет обязательность и тип параметров по сгенерированным интерфейсам. Привязка параметра `severity` принимает ровно одно значение из контракта (`critical`, `major`, `minor`) или его отсутствие. Контроллеры проверяют диапазоны ID и параметров пагинации. Сервис чтения проверяет существование прогона и подразделения, а также известность кода правила.

### 404 Not Found

Возвращается, если:

- указанный `run_id` не существует;
- указанный `unit_id` не существует.

### 422 Unprocessable Entity

Возвращается при некорректных параметрах запроса, например:

- отсутствует обязательный параметр;
- `run_id` или `unit_id` меньше либо равен нулю;
- указан неподдерживаемый `severity`;
- указан неподдерживаемый `rule_code`;
- `limit <= 0` или `limit > 500`;
- присутствующий пустой ID или несколько значений одного ID;
- `offset < 0`;
- параметр имеет некорректный формат.

### Единый формат ошибки

```json
{
  "error": {
    "code": "RESOURCE_NOT_FOUND",
    "message": "Прогон 999 не найден"
  }
}
```

## 11. Стартовые данные

Стартовые данные загружаются миграциями Liquibase.

Демоданные содержат:

- 24 цели, из них 20 активных;
- шесть подразделений на трёх уровнях. Это расширение демонстрации относительно двух–трёх подразделений в исходном backend-ТЗ; согласование требует подтверждения, см. acceptance.md;
- ключевые результаты;
- два прогона ККД;
- нарушения каждого из четырёх реализованных правил;
- проблемы, позволяющие продемонстрировать категории `new`, `persisting` и `resolved`.

Результаты обоих демопрогонов заранее сохранены в миграциях. Для расчёта метрик принято, что в обоих прогонах было по 20 активных целей с одинаковым распределением по подразделениям. Проблемы каждого прогона задаются в `013-insert-kkd-issues.xml`, а рассчитанные по ним метрики сохраняются в `014-insert-kkd-run-metrics.xml`.

## 12. Миграции

Для управления схемой и стартовыми данными используется Liquibase.

Миграции должны поддерживать полный цикл:

```text
накат
→ откат
→ повторный накат
```

без ошибок и ручного изменения состояния БД.

Для changeset, изменяющих схему или стартовые данные, должен быть предусмотрен соответствующий rollback.

При запуске приложения необходимые миграции применяются автоматически.

Compose передаёт приложению параметры подключения через переменные окружения. Значения для локального запуска заданы по умолчанию, переопределить их можно в `.env`. Команды проверки миграций на отдельной базе описаны в [README](../README.md#тесты-и-миграции).

## 13. Ключевые решения

- Для HTTP API выбран подход **API-first** с OpenAPI. Маршруты, параметры, поля ответов и ошибки описаны в одном контракте, по которому фронтенд может работать независимо от реализации сервиса. Maven генерирует из контракта интерфейсы контроллеров и модели ответов, поэтому эти определения больше не дублируются в рукописном Java-коде. Если изменение контракта затрагивает сигнатуру метода или конструктор модели, компиляция выявляет места, где нужно обновить контроллер или маппер. [Контракт API](../src/main/openapi/kkd.yaml)
- Бизнес-логика проверки правил, расчёта метрик и сравнения прогонов отделена от REST API и слоя доступа к данным.
- Каждое правило реализует интерфейс `QualityRule`. `RuleChecker` последовательно вызывает четыре реализации для активной цели.
- Проверки применяются только к активным целям и связанным с ними ключевым результатам.
- Иерархия подразделений реализуется через self-reference `unit.parent_id`.
- Каскадирование целей поддерживается через self-reference `goal.parent_goal_id`.
- Метрики подразделения рассчитываются с учётом всех его дочерних подразделений независимо от глубины вложенности.
- Каждый прогон хранится отдельно и содержит `snapshot_date`.
- Сравниваемый прогон задаётся явно через `kkd_run.compared_to_run_id`.
- Идентичность проблемы между прогонами определяется комбинацией `rule_id + object_type + object_id`.
- Дельта метрики рассчитывается как `current - previous`.
- `trend` определяется семантикой конкретной метрики и может принимать значения `better`, `worse` и `same`.
- Для первого прогона прошлые значения, дельты и `trend` возвращаются как `null`.
- Вес ключевого результата хранится как целое число.
- `KR_WEIGHTS_SUM` применяется к целям с КР и считается выполненным, только если все веса указаны и их сумма равна `100`.
- `KR_STALE_PROGRESS` считается нарушенным, если факт не обновлялся более 45 календарных дней по датам в UTC либо `last_fact_update` отсутствует.
- Все расчёты метрик, дельт и классификация проблем выполняются на backend.
