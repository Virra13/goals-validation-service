# Соответствие backend-ТЗ и ограничения реализации

Источник требований — «Тестовое задание для Backend-разработчика (Java)» (`ac3d0bf0-c031-4475-b9e0-62fe110acc31.pdf`, 3 страницы). Общая презентация проекта используется только как контекст и не расширяет объём задания.

## Требования backend-задания

| Требование | Реализация и проверка |
|---|---|
| Java 17+, Spring Boot 3, PostgreSQL 15+, Maven | Spring Boot сервис; исполняемый JAR собран и проверен через HTTP |
| Разделение API, сервисов, доступа к данным и правил | Слои controller/service/repository/domain; доменные вычисления не зависят от Spring и БД |
| Четыре правила для активных целей и КР | GOAL_NO_OWNER, GOAL_NO_KR, KR_WEIGHTS_SUM, KR_STALE_PROGRESS; граничные сценарии проверены JUnit |
| Метрики подразделения с дочерними подразделениями и сравнение прогонов | Четыре метрики, разбивка важности, new/persisting/resolved, null для отсутствующего сравнения |
| Три GET API, фильтры, пагинация и единые ошибки | Реализованы /api/runs, /api/kkd/summary, /api/kkd/issues; проверены 404/422, фильтры и limit/offset/total |
| Миграции с откатом и стартовые данные | Liquibase; проверены полный и частичный откат с повторным накатом; отличия демоданных перечислены ниже |
| Запуск одной командой docker compose up | Dockerfile и Compose присутствуют; прямой запуск Compose не проверен |
| Автоматические тесты, README и спецификации при использовании ИИ | 44 сценария, инструкции запуска и проверки миграций, requirements.md и design.md |

## Решения в рамках backend-задания

### Запуск и жизненный цикл прогонов

Обязательны три GET API. Ни POST запуска, ни встроенный cron, ни очередь в backend-задании не требуются. Упоминание еженедельной проверки в бизнес-кейсе не задаёт технический механизм планирования.

`KkdRunExecutionService.execute(comparedToRunId)` остаётся внутренним application-сервисом. Он исполняется в интеграционных тестах; после обычного запуска приложения автоматически доступны только демопрогоны. Если понадобится внешний запуск новых проверок, потребуется вызывающий адаптер: задача планировщика, worker или служебная команда. Такой адаптер не входит в обязательный объём backend-задания.

Прогон, проблемы и метрики сохраняются атомарно в одной REPEATABLE_READ-транзакции. RUNNING извне не наблюдается, неудачная попытка не сохраняется как FAILED. Это ограничение текущей синхронной реализации. Для мониторинга попыток нужен отдельный журнал выполнения; разрывать транзакцию результатов ради наблюдаемого статуса нельзя без дополнительного проектирования. Базой сравнения может быть только COMPLETED-прогон.

### Оргструктура и история

Требование backend-задания явно задаёт учёт дочерних подразделений. Проверка `CASCADE_NO_PARENT` является одним из шести вариантов, из которых выбираются четыре; она не выбрана и не является обязательной пятой проверкой. Связь `goal.parent_goal_id` хранится, но цель не должна повторно попадать в метрики одновременно через дерево целей и дерево подразделений.

Текущая модель хранит подразделение проблемы на момент прогона, но не версию дерева подразделений. Метрики сохранены по дереву на момент расчёта, а списки проблем и их сравнение используют текущее поддерево. Поэтому для согласованной исторической сводки необходимо, чтобы оргструктура не менялась между расчётом и чтением сравниваемых прогонов. Это ограничение реализации, не требование заказчика.

Для поддержки реорганизаций нужно определить семантику: историческая оргструктура каждого прогона или единый текущий состав. Для первого варианта требуется снимок/версия иерархии; для второго — хранение исходных счётчиков для пересчёта метрик по тому же составу. Одна только смена SQL-фильтра без изменения хранения проблему не решит. Текущая правка производительности не меняет это поведение.

### Правила и формулы

Выбраны GOAL_NO_OWNER, GOAL_NO_KR, KR_WEIGHTS_SUM и KR_STALE_PROGRESS с важностями из backend-ТЗ. Их набор и важность фиксированы кодом. Справочник БД хранит идентификаторы и описания; `is_active` не является реализованной настройкой включения/отключения проверок, изменение справочника не переопределяет Java-правила. Runtime-управление правилами исходным backend-заданием не предусмотрено. Если оно потребуется, нужно версионирование набора правил для сопоставимых прогонов.

Наличие ответственного и корректность весов рассчитываются по данным цели общими предикатами `GoalQuality`, а не по отсутствию строкового кода нарушения. Это устраняет зависимость этих двух метрик от полноты findings. «Доля корректных целей» и «проблем на цель» по определению используют полный результат проверки выбранными четырьмя правилами.

Дополнительные трактовки текущего design.md: пустой/пробельный owner считается отсутствующим; отсутствие КР даёт GOAL_NO_KR без дополнительного KR_WEIGHTS_SUM; null-вес нарушает KR_WEIGHTS_SUM; null-дата факта нарушает KR_STALE_PROGRESS; давность считается по календарным дням UTC, ровно 45 дней допустимо. Это явно зафиксированные решения для случаев, не детализированных в backend-ТЗ.

### Технические ограничения

- Дерево загружается одним запросом, счётчики суммируются снизу вверх без рекурсии Java. Агрегация O(U + G + K + F); проценты округляются после суммирования числителей и знаменателей.
- Результаты записываются JDBC-пакетами по 250 строк в общей транзакции с JPA-прогоном; IDENTITY в схеме сохраняется. Для драйвера PostgreSQL включён `reWriteBatchedInserts`.
- Сводка читает проекции ключей и важности без текстов описаний и JPA-сущностей проблем. Классификация остаётся в чистом домене. Память всё ещё O(F) для сравниваемых проблем; это не решение для неограниченного объёма данных.
- Выполнение прогона пока читает все активные цели и КР в память. Для больших объёмов нужны измерения и, при необходимости, порционная обработка с сохранением согласованности снимка.
- Диапазон страницы: `1 <= limit <= 500`, `offset >= 0`. Верхняя граница 500 добавлена как ограничение этого API, а не извлечена из исходного PDF. Пустой переданный ID — 422; отсутствие необязательного unit_id разрешено.
- `spring.jpa.open-in-view=false`, схема проверяется через `ddl-auto=validate`. Сервис по умолчанию использует системное время UTC; Clock-бин с фиксированным временем объявлен только в тестовой конфигурации. Параметр JVM задан через `JAVA_TOOL_OPTIONS`.

## Явные отличия демоверсии от исходных материалов

1. В backend-PDF указаны 20–30 целей в двух–трёх подразделениях. Здесь 24 цели в шести подразделениях на трёх уровнях. Это расширение демонстрации иерархии; подтверждения согласования с заказчиком в предоставленных материалах нет. Для строгой сдачи нужно согласовать отклонение либо адаптировать seed-данные и ожидаемые метрики отдельным изменением.
2. В примере backend-ТЗ `unit.id` имеет вид `"HQ-CIB"`. В текущем API идентификатор подразделения — число. Это отличие от примера ответа: при строгом требовании к его типу потребуется бизнес-код подразделения и адаптация контракта.

## Выполненная локальная проверка

Среда проверки: Windows, JDK 21, PostgreSQL 18.6, отдельный временный кластер и отдельные БД для интеграционных тестов и миграций. В Docker Compose по-прежнему задан PostgreSQL 15. Прямой запуск Docker Compose не выполнялся.

- 44 тестовых сценария: 38 без БД и 6 с PostgreSQL; ошибок и пропусков при полном запуске нет.
- Проверены 12 000 уровней дерева, разные знаменатели дочерних подразделений, пустые подразделения, циклы дерева и независимость метрик owner/weights от findings.
- Добавление 100 подразделений не увеличило число подготовленных JPA SQL-команд выполнения прогона. JDBC-пакеты результатов закономерно растут с количеством записываемых строк.
- Проверены сохранение 610 проблем через несколько пакетов и полный откат JPA-прогона/JDBC-проблем при отказе вставки метрик.
- Проверены контракт ошибок, фильтры, offset/total, явные null первого прогона и запрет сравнения с незавершённым прогоном.
- Успешно собран и запущен исполняемый JAR; GET вернули два демопрогона, четыре метрики и дельту 6 новых / 4 сохраняющихся / 3 исправленных.
- На отдельной БД выполнены update → rollback(14) → update и rollback(7 seed-changeset) → update. Итог: 2 прогона, 24 цели, 17 проблем, 48 метрик и 14 записей databasechangelog.

Результаты относятся к указанной локальной среде. Проверка запуска через Docker Compose остаётся невыполненной.
