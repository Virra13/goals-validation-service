## Назначение системы
Сервис предназначен для автоматизации проверки качества данных по целям сотрудников и ключевым результатам.  
Сервис выявляет нарушения установленных правил качества данных, сохраняет результаты каждого прогона проверки и предоставляет через REST API агрегированную статистику, сведения о найденных проблемах и динамику изменений качества данных.

## Бизнес-требования
BR-01. Система должна обеспечивать пользователей аналитикой по качеству ведения целей и ключевых результатов.

BR-02. Система должна выявлять нарушения правил качества данных при заполнении целей и ключевых результатов, позволяя пользователям своевременно обнаруживать и исправлять ошибки.

BR-03. Система должна наглядно отображать изменения качества данных по сравнению с предыдущим отчетным периодом для оценки прогресса подразделений.

BR-04. Расчёт метрик качества данных по подразделению должен учитывать данные всех его дочерних подразделений независимо от глубины вложенности.

## Функциональные требования
### Получение и хранение данных
FR-01	Система должна получать данные о подразделениях, целях и ключевых результатах из БД.

FR-02	Система должна хранить справочник правил ККД в БД.

FR-03	Система должна сохранять результаты каждого прогона ККД и связанные с ним найденные проблемы в БД.

### Проверка качества данных

FR-04	Система должна проверять данные по четырём выбранным правилам ККД.

FR-05	Проверки должны применяться только к активным целям и связанным с ними ключевым результатам.

FR-06	Каждая найденная проблема должна содержать информацию о правиле, объекте проверки, уровне важности и описании нарушения.

### Расчёт метрик и сравнение прогонов

FR-07	Система должна рассчитывать метрики качества данных по подразделению с учётом всех его дочерних подразделений.

FR-08	Система должна сравнивать текущий прогон с прогоном, указанным для него как предыдущий (compared_to_run_id).

FR-09	Система должна определять идентичность проблем по совпадению правила и объекта проверки.

FR-10	Система должна классифицировать проблемы как новые, сохраняющиеся и исправленные.

FR-11	Для прогона без сравнения предыдущие значения, дельты метрик и разбивки по важности, тренды метрик и объект сравнения проблем должны быть null.

### REST API

FR-12	Система должна предоставлять список прогонов через **GET /api/runs**, содержащий статус, дату снимка, идентификатор сравниваемого прогона и количество найденных проблем.

FR-13	Система должна предоставлять сводную статистику через **GET /api/kkd/summary?run_id=&unit_id=**, включающую:
- не менее трёх метрик с текущими и предыдущими значениями, дельтой и направлением изменения;
- разбивку проблем по уровням важности;
- количество новых, сохраняющихся и исправленных проблем.

FR-14	Система должна предоставлять список проблем через **GET /api/kkd/issues** с фильтрацией по подразделению, правилу и важности, а также пагинацией (limit, offset, total).

FR-15. Система должна проверять входные параметры запросов на обязательность, формат и допустимые значения. 

FR-15a. Присутствующий пустой ID считается некорректным параметром (422). Отсутствие необязательного unit_id допускается. Максимальный размер страницы — 500; значения limit вне 1–500 возвращают 422.

### Обработка ошибок

FR-16	Система должна возвращать HTTP 422 при передаче некорректных параметров запроса. 

FR-17	Система должна возвращать HTTP 404 при обращении к несуществующему прогону или подразделению.

FR-18	Ошибки 404 и 422 из FR-16 и FR-17 должны возвращаться в едином формате `{"error": {"code": "...", "message": "..."}}`.

## Технические и архитектурные требования
ARCH-01. Бизнес-логика проверки ККД, расчёта метрик и сравнения прогонов должна быть отделена от REST API и слоя доступа к данным.

ARCH-02. Проект должен предусматривать разделение на контроллеры, сервисный слой и слой доступа к данным.

ARCH-03. Схема данных PostgreSQL должна предусматривать сущности подразделений, целей, ключевых результатов, правил ККД, прогонов и найденных проблем.

ARCH-04. Расчёты метрик, классификация проблем и вычисление дельт должны выполняться на стороне backend. Frontend должен получать готовые результаты через REST API и не должен самостоятельно рассчитывать метрики, фильтровать исходные данные или определять изменения между прогонами.

TECH-01. Стек Java 17+, Spring Boot 3, PostgreSQL 15+, Maven.

TECH-02. Для управления структурой БД используется Liquibase.

TECH-03. Миграции должны поддерживать механизм отката (rollback).

DEPLOY-01. Сервис и PostgreSQL должны запускаться с помощью Docker Compose командой docker compose up.

DEPLOY-02. Запуск приложения должен предусматривать автоматическое применение необходимых миграций БД.

DEPLOY-03. Конфигурация приложения должна задаваться через переменные окружения.

DEPLOY-04. В репозитории должен присутствовать файл .env.example, содержащий перечень необходимых переменных окружения и примеры значений.

QA-01. Бизнес-логика должна быть покрыта автоматическими тестами с использованием JUnit 5.

QA-02. Минимальный набор тестовых сценариев должен включать:
- проверку двух правил ККД на граничных данных;
- проверку расчёта метрик;
- проверку расчёта дельты между прогонами.

DELIVERY-01. Стартовые данные должны содержать 20–30 целей в двух-трёх подразделениях.

DELIVERY-02. Стартовые данные должны включать два прогона ККД.

DELIVERY-03. В стартовых данных должны присутствовать нарушения каждого выбранного правила, а результаты двух прогонов должны позволять продемонстрировать сравнение проблем.

DELIVERY-04. Каждая миграция, изменяющая схему или стартовые данные, должна иметь корректный rollback, позволяющий выполнить update → rollback → update без ошибок.

## Реализуемые бизнес-правила ККД
BR-KKD-01: **GOAL_NO_OWNER**
- Проверяются только активные цели.
- Если у цели отсутствует ответственный, создаётся проблема.
- Важность проблемы — critical.

BR-KKD-02: **GOAL_NO_KR**
- Проверяются только активные цели.
- Если у цели нет ни одного ключевого результата, создаётся проблема.
- Важность проблемы — critical.

BR-KKD-03: **KR_WEIGHTS_SUM**
- Проверяются ключевые результаты активной цели.
- Сумма весов всех ключевых результатов должна составлять 100%.
- Если сумма отличается от 100%, создаётся проблема.
- Важность — major.

BR-KKD-04: **KR_STALE_PROGRESS**
- Для каждого ключевого результата активной цели проверяется дата последнего обновления фактического значения.
- Если факт ключевого результата не обновлялся более 45 дней, создаётся проблема.
- Важность — minor.

## User Stories и критерии приёмки
### US-01. Аналитика качества данных. 
> **Как** пользователь сервиса,  
> **Я хочу** видеть количественные и качественные метрики по целям и ключевым результатам моего подразделения с учётом иерархии подразделений,  
> **Чтобы** находить ошибки заполнения и оценивать качество данных процесса планирования.

US-01-AC-01. Backend возвращает не менее трёх агрегированных метрик качества данных для запрошенного подразделения (unit_id).

US-01-AC-02. При расчёте метрик учитываются данные запрошенного подразделения и всех его дочерних подразделений, включая вложенные уровни.

US-01-AC-03. Backend возвращает количество найденных проблем с группировкой по уровням важности (severity).

US-01-AC-04. При обнаружении активной цели без ответственного создаётся проблема GOAL_NO_OWNER с уровнем важности critical.

US-01-AC-05. При обнаружении активной цели без ключевых результатов создаётся проблема GOAL_NO_KR с уровнем важности critical.

US-01-AC-06. При обнаружении активной цели, сумма весов ключевых результатов которой отличается от 100%, создаётся проблема KR_WEIGHTS_SUM с уровнем важности major.

US-01-AC-07. Если факт ключевого результата активной цели не обновлялся более 45 дней, создаётся проблема KR_STALE_PROGRESS с уровнем важности minor.

US-01-AC-08. Каждая найденная проблема содержит идентификатор правила, объект проверки, уровень важности и описание нарушения.

### US-02. Мониторинг динамики качества данных (дельта).
> **Как** пользователь сервиса,  
> **Я хочу** видеть изменения (дельту) метрик качества по сравнению с прошлым прогоном ККД,  
> **Чтобы** оценивать динамику исправления ошибок и изменения качества данных.

US-02-AC-01. Каждый завершённый прогон сохраняется в БД вместе с результатами проверки и найденными проблемами.

US-02-AC-02. Результаты разных прогонов хранятся отдельно и доступны для последующего сравнения.

US-02-AC-03. Для каждой метрики backend возвращает текущее и предыдущее значения, разницу между ними и направление изменения (`better`, `worse` или `same`). Если одного из значений нет, дельта и направление равны `null`.

US-02-AC-04. Backend классифицирует проблемы по результатам сравнения прогонов и возвращает количество: новых (new) — обнаруженных только в текущем прогоне; сохраняющихся (persisting) — присутствовавших в предыдущем и текущем прогонах; исправленных (resolved) — присутствовавших в предыдущем, но отсутствующих в текущем прогоне.

US-02-AC-05. Проблемы считаются идентичными, если совпадают правило и объект проверки. При наличии такой проблемы в обоих сравниваемых прогонах она классифицируется как persisting.

US-02-AC-06. Если у текущего прогона отсутствует предыдущий прогон для сравнения, предыдущие значения и дельты метрик возвращаются как null, а не 0.

US-02-AC-07. Backend предоставляет список выполненных прогонов через GET /api/runs, содержащий статус, дату снимка, идентификатор сравниваемого прогона и количество найденных проблем.
