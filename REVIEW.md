## 1. Подтверждённые замечания

### R1. P2 — N+1 запросов и повторный полный обход данных при расчёте метрик

Место: [KkdRunExecutionService.java:174](E:/kkd/src/main/java/ru/virra/kkd/service/KkdRunExecutionService.java:174).

`units.findAll()` выполняется один раз, затем `findSubtreeIds(unit.getId())` вызывается для каждого подразделения. Для U подразделений это 1 + U запросов только на иерархию. Внутри того же цикла заново фильтруются все цели и все нарушения, а `MetricsCalculator` ещё раз группирует нарушения и обходит отобранные цели.

Следствие: как минимум O(U × (G + F)) работы по фильтрации, где G — число активных целей, F — число нарушений, плюс повторные рекурсивные запросы. На шести подразделениях это малозаметно, при росте дерева становится существенным.

Исправление: получить `id, parent_id` всех подразделений одним запросом, посчитать локальные счётчики по каждому подразделению и сложить их снизу вверх по дереву. Передавать числители и знаменатели метрик, а проценты рассчитывать после агрегации: усреднять готовые проценты дочерних подразделений нельзя. Для корректного дерева это позволяет приблизиться к O(U + G + F).

Проверка исправления: фиксированное число SELECT при увеличении количества подразделений; одинаковые метрики на деревьях разной глубины и с разным количеством целей в ветвях.

### R2. P2 — `saveAll()` не даёт пакетной вставки результатов

Места: [KkdRunExecutionService.java:90](E:/kkd/src/main/java/ru/virra/kkd/service/KkdRunExecutionService.java:90), [KkdIssue.java:33](E:/kkd/src/main/java/ru/virra/kkd/entity/KkdIssue.java:33), [KkdRunMetric.java:31](E:/kkd/src/main/java/ru/virra/kkd/entity/KkdRunMetric.java:31).

Обе массово записываемые сущности используют `GenerationType.IDENTITY`; JDBC batching в настройках также не включён. Сохранение F нарушений и четырёх метрик для U подразделений приводит к F + 4U отдельным INSERT, несмотря на название `saveAll()`.

Это отдельная проблема от N+1 чтения. Для IDENTITY Hibernate не выполняет batching INSERT; одного добавления `hibernate.jdbc.batch_size` недостаточно. См. [документацию Hibernate 6.6](https://docs.hibernate.org/orm/6.6/userguide/html_single/#identifiers-generators-identity).

Исправление: для результатов использовать JDBC `batchUpdate`, либо перейти на `SEQUENCE` с согласованными настройками генератора и миграциями и включить JDBC batching. Пакеты сохранять в той же транзакции. При большом объёме также ограничить число удерживаемых JPA-сущностей; само пакетирование запросов расход памяти не исправляет.

### R3. P2 — сводка загружает все нарушения обоих прогонов

Место: [KkdSummaryService.java:70](E:/kkd/src/main/java/ru/virra/kkd/service/KkdSummaryService.java:70).

Для небольшого агрегированного ответа загружаются полные `KkdIssue`, включая текст описания, для текущего и предыдущего прогонов. Затем создаются дополнительные множества ключей. Размер ответа почти постоянный, но расход памяти и CPU линейно зависит от количества проблем; повторные запросы повторяют всю работу.

Это избыточная загрузка данных, а не установленный N+1: обращение к ID правила само по себе не является доказательством дополнительного SELECT на каждую строку.

Первый шаг: узкая проекция `ruleId, objectType, objectId, severity`, позволяющая сохранить текущий чистый `RunComparator`. При больших объёмах — агрегации `GROUP BY severity` и подсчёт пересечений/разностей на стороне БД. Такой перенос остаётся расчётом на backend, но требует согласовать границу доменных вычислений и repository с ARCH-01. Добавлять кэш стоит после определения стабильности исторического среза.

### R4. P2 — пустой `unit_id` незаметно снимает фильтр

Места: [KkdIssueController.java:33](E:/kkd/src/main/java/ru/virra/kkd/controller/KkdIssueController.java:33), [KkdIssueQueryService.java:38](E:/kkd/src/main/java/ru/virra/kkd/service/KkdIssueQueryService.java:38).

Проверено через standalone MockMvc:

```text
GET /api/kkd/issues?run_id=1&unit_id= → HTTP 200
GET /api/kkd/issues?run_id=1&unit_id=abc → HTTP 422
```

Пустая строка необязательного `Long` превращается в `null`. Контроллер её пропускает, сервис не применяет фильтр подразделений. Пользователь передал параметр неверного формата, а получил результат для всего прогона. Это расходится со строгим прочтением FR-15/FR-16 и типом `PositiveId` в OpenAPI.

Исправление: различать отсутствие параметра и присутствующий пустой параметр на границе HTTP, возвращая для второго 422. Зафиксировать это в MVC-тестах. Дополнительно определить политику повторяющихся числовых параметров: сейчас `run_id=1&run_id=2` и `limit=5&limit=-1` принимаются с первым значением. Отдельного требования об их кратности в ТЗ нет, поэтому это рекомендация, а не самостоятельное нарушение.

### R5. P2 — у размера страницы нет верхней границы

Места: [KkdIssueController.java:38](E:/kkd/src/main/java/ru/virra/kkd/controller/KkdIssueController.java:38), [KkdIssueSearchRepository.java:53](E:/kkd/src/main/java/ru/virra/kkd/repository/KkdIssueSearchRepository.java:53).

MockMvc подтвердил, что `limit=2147483647` проходит валидацию и передаётся сервису. JDBC затем собирает всю полученную страницу в `List`, а контроллер создаёт список DTO. На большом прогоне один запрос фактически может отключить пагинацию и вызвать длительную обработку или нехватку памяти.

Исправление: согласовать максимальный размер страницы, например 100–500, задать его в OpenAPI и проверке контроллера. Значение выше максимума возвращать как 422. Это усиление эксплуатационных ограничений: текущее ТЗ задаёт только нижнюю границу.

### R6. P3 — `JAVA_OPTS` в Dockerfile не применяется

Место: [Dockerfile:15](E:/kkd/Dockerfile:15).

Задано `JAVA_OPTS="-XX:MaxRAMPercentage=75"`, но процесс запускается как `java -jar app.jar`. Переменная не передаётся Java ни аргументом, ни скриптом запуска. Поэтому указанная настройка памяти не действует.

Исправление: использовать поддерживаемую JVM переменную `JAVA_TOOL_OPTIONS` либо явно передать флаг в ENTRYPOINT. JSON/exec-форма сама по себе не подставляет переменные; см. [документацию Docker](https://docs.docker.com/reference/dockerfile/#variable-substitution).

## 2. Ограничения архитектуры и уточнения ТЗ

### A1. Нет точки запуска проверки

Место: [KkdRunExecutionService.java:70](E:/kkd/src/main/java/ru/virra/kkd/service/KkdRunExecutionService.java:70).

По поиску всего `src` у `execute()` нет вызывающего кода. Нет запускающего контроллера, планировщика, CLI-команды или listener. После старта приложение обслуживает демопрогоны, но изменение целей само по себе не приводит к новому расчёту и вызвать его штатным способом нельзя.

Это функциональный пробел для самостоятельного сервиса автоматических проверок. При этом `design.md` прямо называет сервис внутренним, а обязательный HTTP-контракт содержит только GET. Поэтому отсутствие POST нельзя объявлять нарушением конкретного REST-требования.

Перед практическим использованием выбрать один способ запуска: служебная команда, планировщик или защищённая операция API. Для демонстрации достаточно минимальной команды; очередь и отдельный worker сейчас не обязательны. Добавить сценарий «запустить → изменить цель → запустить повторно → прочитать дельту».

### A2. Историческая сводка смешивает два разных среза иерархии

Место: [KkdSummaryService.java:64](E:/kkd/src/main/java/ru/virra/kkd/service/KkdSummaryService.java:64). Основание: [design.md:276](E:/kkd/specs/design.md:276).

Метрики сохраняются для поддерева на дату прогона. Проблемы выбираются по текущему дереву подразделений. Если перенести подразделение B из A в C, метрики старого прогона для A продолжат учитывать B, а количество и список проблем A перестанут учитывать B. Исторический ответ изменится без нового прогона.

Это намеренное решение текущего design.md, а не отклонение реализации от него. Для воспроизводимых отчётов стоит изменить проектирование: хранить состав поддерева для прогона или версию оргструктуры и применять один срез ко всем частям ответа. Альтернативный продуктовый смысл — отчёт по текущей структуре — тоже возможен, но тогда нужны исходные счётчики/данные, позволяющие пересчитать и метрики в том же составе.

### A3. Два источника описания правил

Места: [RuleChecker.java:13](E:/kkd/src/main/java/ru/virra/kkd/domain/rule/RuleChecker.java:13), [KkdRunExecutionService.java:145](E:/kkd/src/main/java/ru/virra/kkd/service/KkdRunExecutionService.java:145).

В БД есть `is_active` и `severity`, но проверяющий код всегда запускает четыре фиксированных правила и берёт severity из Java. Изменение этих полей справочника не меняет проверку. Для ТЗ с четырьмя фиксированными правилами это не доказанная ошибка расчёта; возможность отключать их через БД не задана.

Нужно выбрать один источник истины. Если справочник — только метаданные фиксированных правил, явно закрепить это и проверять согласованность при старте. Если он должен управлять выполнением, передавать доменному checker набор конфигураций из application-слоя, сохранять версию/состав правил прогона. Не добавлять обращения в БД внутрь каждого правила.

### A4. Калькулятор метрик имеет неявный контракт полноты findings

Место: [MetricsCalculator.java:40](E:/kkd/src/main/java/ru/virra/kkd/domain/metric/MetricsCalculator.java:40).

Наличие ответственного и корректность весов определяются отсутствием нарушений с определённым строковым кодом. Например, цель с `ownerId=null` и пустым списком findings даст 100% целей с ответственным. Текущий execution-сервис передаёт полный результат всех правил, поэтому в его штатном пути это не самостоятельный дефект.

Риск проявится при отключении правила, неполной проверке или переименовании кода. Вынести общие предикаты `hasOwner` и `hasValidWeights` и использовать их в правилах и соответствующих метриках либо ввести тип полного результата проверки, который гарантирует выполненный набор правил. Строковые коды правил заменить общим типом `RuleCode`.

### A5. Жизненный цикл прогона пока не даёт мониторинга выполнения

Место: [KkdRunExecutionService.java:69](E:/kkd/src/main/java/ru/virra/kkd/service/KkdRunExecutionService.java:69).

Весь расчёт и запись идут одной транзакцией: RUNNING не виден другим транзакциям, а при ошибке исчезает весь прогон. FAILED нигде не устанавливается. При этом `resolvePreviousRun` проверяет только наличие записи, не её статус. Если появится незавершённый/ошибочный прогон, его можно будет выбрать базой сравнения.

Одна транзакция соответствует design.md и обеспечивает атомарность результатов, поэтому разрывать её только ради формальных статусов не стоит. Если вводится асинхронное выполнение, отдельно спроектировать журнал попыток/статусов, сохранение ошибки вне откатившейся транзакции и разрешение сравнения только с COMPLETED. Снимок исходных данных должен оставаться согласованным.

## 3. Что улучшить без усложнения системы

- Сохранить слоистый модульный монолит и чистые доменные классы. Сочетание JPA для записи и JDBC для выборки страницы само по себе уместно.
- Выделить расчёт агрегированных счётчиков по дереву в чистый компонент; execution-сервис оставить координатором загрузки, проверки и сохранения. Наличие семи репозиториев в координаторе ещё не делает его «God Object».
- Внедрить `Clock` вместо прямых `Instant.now()`, чтобы воспроизводимо проверять даты запуска и границы суток UTC.
- Отключить Open Session in View и явно установить `ddl-auto=validate`, чтобы границы доступа к данным и соответствие миграций сущностям проверялись явно. Это профилактика, не найденный N+1.
- Рассмотреть индексы `kkd_issue(run_id, unit_id)` для сводки и `(run_id, id)` для страницы. Проверить кандидаты через `EXPLAIN (ANALYZE, BUFFERS)` на реалистичных данных; добавлять все комбинации фильтров без измерений не нужно.
- Для массовой загрузки КР вместо огромного `IN (:goalIds)` рассмотреть проекцию с JOIN на активные цели. Для текущих 24 целей это не срочно.
- Удалить неиспользуемые производные методы репозиториев после проверки будущих сценариев. Обобщённые base-service и универсальные мапперы ради устранения нескольких строк не нужны.
- Демоданные при дальнейшем использовании вынести в отдельный Liquibase context/profile. В текущем ТЗ их автоматическая загрузка является требованием.

## 4. Проверки и границы уверенности

Выполнено:

- Изучены обе спецификации, основной Java-код, тесты, контракт, конфигурация, схема БД и структура миграций.
- `mvn -o test` с локальным Maven-кэшем и JDK 21: успешно, 13 сценариев, 0 ошибок, 0 пропусков. Сборка включает генерацию OpenAPI и компиляцию.
- Временный standalone MockMvc probe: 19 запросов с отсутствующими, пустыми, некорректными, повторяющимися и граничными параметрами. Использованы настоящие контроллер и advice, сервис заменён stub; это проверяет HTTP-привязку и валидацию, а не обращения в БД.
- Основные случаи обязательности, формата, диапазонов и severity возвращают 422. Отображение исключения отсутствующего ресурса в 404 также проверено.
- Статически проверено наличие rollback у всех 14 changeset, порядок отката данных и настройка последовательностей для явных ID. Ссылки на правила в seed-проблемах берутся по `code`, а не по предположению об ID 1–4.

Не выполнялись: запуск полного приложения с PostgreSQL, Docker Compose, реальный `update → rollback → update`, измерение SQL-счётчиков и нагрузочное тестирование. Наличие rollback в XML не доказывает успешное выполнение цикла на БД.

В существующем наборе нет интеграционных тестов сервисов/репозиториев и постоянных MVC-тестов. Минимум QA-02 покрыт, но этого недостаточно для проверки всех требований.

Следующие тесты имеют наибольшую ценность:

1. PostgreSQL: новый прогон, сохранение четырёх метрик для каждого подразделения, уникальность проблем, откат всех результатов при ошибке.
2. Иерархия: несколько уровней, пустое подразделение, разные знаменатели у дочерних узлов, согласованный исторический срез после переноса ветви.
3. HTTP: 404/422 и единый JSON, первый прогон с явными null, фильтры, offset/total, пустой unit_id и максимальный limit.
4. Liquibase: полный и частичный откат seed-миграций с повторным накатом на изолированной БД.
5. SQL-счётчик: число запросов чтения дерева не растёт линейно с числом подразделений после исправления R1.

## 5. Приоритет работ

Для сдачи демонстрации: исправить пустой фильтр и неработающий JAVA_OPTS, определить способ запуска новых прогонов, добавить MVC- и PostgreSQL-проверки критических сценариев.

Перед ростом данных: устранить N+1 расчёта дерева, пакетировать вставки, ограничить размер страницы и уменьшить объём данных сводки.

Перед регулярной эксплуатацией: согласовать историческую оргструктуру, управление правилами и жизненный цикл прогонов. Эти изменения требуют обновления design.md, поскольку затрагивают семантику системы.

Исходный код приложения не изменялся. Дополнительный диагностический probe находится в `target/review/ReviewProbe.java` и не является частью постоянного тестового набора.
